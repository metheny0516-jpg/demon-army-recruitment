## 取り込みの手順（上がったと報告されたら）
1. git fetch。枝が本線から切られているか確認（merge-base）。古い土台なら乗り換えさせる。
2. 差分を読む。担当外の層（例：CodeX が src/core を触っている）は差し戻す。
3. 検証を直列で：node は `for f in tools/test-*.js; do node $f; done`（全通過が前提）。UI を触った変更は `sh tools/browser-tests/run-all.sh`（playwright と Chromium が要る。HANDOFF「テストの回し方」参照）。
4. データや数値を触った変更は `node tools/sim.js 20` を1回。見るのは「0% になった戦略が無いか」「平均戦闘数が急に半分になっていないか」だけ。クリア率を合格帯に合わせる調整はしない（オーナー決定 2026-09-10）。
5. 本線へ入れ、HANDOFF.md 0節の先頭に「済／検証結果／次に誰へ何を」を書いて同じコミットで push。
6. オーナーへ報告：何を・なぜ・どう確認したか・残っている問題・次に誰へ何を貼るか。貼り付け文は仕様書の該当節からそのまま出す。

## 判断の物差し（迷ったら）
- 「実装が簡単だから」で機能を足さない。「既存の何と組み合わさると面白いか」で評価する。接続数がコンテンツ数より大事。
- 恒久成長を「攻撃力+1%」にしない。増やすのは選択肢・組み合わせ・発見・歴史。
- 敗北は笑える／悔しい／人に話したくなるものに。くすっと笑える世界観を守る。
- 削除は「動いているか」ではなく「判断を生んでいるか／別の要素に繋がっているか」で決める。消す前に必ず sim で測る（2026-09-16 に測り方を間違えて一度戻した。docs/AUDIT_DEAD_ELEMENTS_2026-09-15.md の訂正を読むこと）。
- 数値は変えたら測る。測っていない数値の変更は本線に入れない。

## やってはいけないこと
- 既定ブランチや古い枝を土台にした作業を、測り直さずに本線へ入れる。
- HANDOFF を更新せずに終える（次の人が文脈ゼロで拾えなくなる）。
- 二人に同じ run.js のチケットを渡す。
- テストを消す・無効にして通す。

## 環境が無いときの分け方（2026-09-16 追記）
統括役のチャットが node 全件・Chromium・sim を回せないなら、統括を2つに割る。
- 設計・指示役（例：ChatGPT Work）＝ 仕様書・設計レビュー・分担の指示・貼り付け文・HANDOFF の判断待ち欄。**本線へ push しない。** 上がった枝には「入れてよい／差し戻し」の判断とレビューを書くだけ。
- 取り込み・検証役（Claude Code のセッション）＝ fetch → 差分レビュー → node 全件・ブラウザ回帰・sim 20 → 本線へ push → HANDOFF 0節に記録。
本線へ push するのは検証役だけ。実装者（Opus）に自分の変更を検証させない。
