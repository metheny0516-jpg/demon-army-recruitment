## 1. いまの定義とその問題

`emitCausal(type, data, parent)` は、親を持つ因果イベントの深さを**種類を問わず**
`parent.chainDepth + 1` にしている（`src/core/battle.js`）。
その結果、**同じ一つの効果を言い換えただけのイベントも1段として数える**。

例（実測・OVERKILL系統）:

```
 1  attack                     … 殴った（実効果）
 2  overkill                   … その一撃の余剰を言い換えただけ
 3  trait_trigger(chain_massacre) … 「伝播する」という宣言
 4  splash                     … 実際に伝播したダメージ（実効果）
```

プレイヤーから見た出来事は「殴った → 余りが次へ流れた」の**2つ**なのに、記録は4段になる。
そしてこの4という数字が、そのまま**ダメージ倍率 ×1.75**として跳ね返っている。

## 2. 契約案：因果イベントを3つの役に分ける

| 役 | 定義 | 段数 |
|---|---|---|
| **実効果** `effect` | HP・資源・編成・倍率のいずれかを実際に動かす | **+1段** |
| **通知** `notice` | すでに他所で決まっている結果を知らせるだけ | 親と同じ |
| **同一効果の補足** `restate` | 親と同じ一つの効果を言い換える／これから起こすと宣言する | 親と同じ |

判定はイベント種別だけでは足りない（`trait_trigger` と `facility_trigger` が3役を兼ねる）。
`traitId` / `facilityId` / `resource` まで見て決める。

### 2.1 全因果イベントの分類（現行で `emitCausal` から出る全種類）

| イベント | 条件 | 役 | 理由 |
|---|---|---|---|
| `attack` / `splash` | — | 実効果 | HPが減る |
| `death` | — | 実効果 | ユニットが退場し、略奪・墓地・魂の反応がすべてここを親に持つ**分岐点** |
| `revive` / `summon` / `heal` | — | 実効果 | 編成・HPが動く |
| `momentum` | — | 実効果 | 味方全員の与ダメージ倍率が上がる |
| `incident` | — | 実効果 | 仲間割れ。直後に同士討ちのダメージが続く |
| `resource_gain` | gold / soul | 実効果 | 予約金貨・魂が増える |
| `resource_consume` | food | 実効果 | 備蓄が減る |
| `resource_consume` | soul | **補足** | 《魂の徴収》の内訳（同じ一つの効果の後半） |
| `resource_forfeit` | — | 実効果 | 予約金貨が没収される |
| `trait_trigger` | `soul_harvest` / `hunger_demon` / `glutton_feast` | 実効果 | その場で倍率・追加行動を起こす |
| `trait_trigger` | `greedy` / `chain_massacre` / `overload` | **補足** | 「これから起こす」宣言。実効果は直後の子（追加行動・伝播ダメージ）が持つ |
| `trait_trigger` | `demon_cook` / `big_eater` | **通知** | 倍率は出撃前に確定済み（V2aの伝票 `mealPlan`・`preparedRoster` の mods） |
| `synergy_trigger` | `goblin_pair` | 実効果 | 次の味方攻撃 +25% |
| `facility_trigger` | `extortion_ledger` | 実効果 | 次の味方攻撃 +40% |
| `facility_trigger` | `grand_kitchen` | **通知** | 倍率は伝票側で計算済み |
| `facility_trigger` | `graveyard` | **補足** | 実効果は子の `summon` |
| `overkill` | — | **補足** | 同じ一撃の余剰の言い換え |
| `survive` | — | **通知** | `onLethal` がすでに救っている |

**新定義（D2）**: `chainDepth` は役が `effect` のときだけ +1 する。
`notice` / `restate` は親の深さを継承する。全因果イベントは `chainRole` を持つ。

## 3. 5系統の期待経路（実測・編成とseed固定）

`node tools/chain-audit.js --paths` が毎回この経路を出す。左が現行、右が新定義。

| 系統 | 経路 | 現行 → 新定義 |
|---|---|---|
| 略奪 | `attack` →[実]`resource_gain(gold)` →[補]`trait_trigger(greedy)` →[実]`attack` | **4 → 3** |
| 食料 | `resource_consume(food)` →[通]`facility_trigger(grand_kitchen)` | **2 → 1** |
| 死霊 | `attack` →[実]`death` →[実]`revive` →[実]`trait_trigger(soul_harvest)` | **4 → 4**（変わらない） |
| 召喚 | `attack` →[実]`death` →[補]`facility_trigger(graveyard)` →[実]`summon` | **4 → 3** |
| OVERKILL | `attack` →[補]`overkill` →[補]`trait_trigger(chain_massacre)` →[実]`splash` | **4 → 2** |

読み方: **死霊系統だけが現行のまま**で、他の4系統は1〜2段下がる。
とくにOVERKILLの伝播は「見かけ上いちばん深い連鎖」だったが、
実際に起きている出来事は2つしかない。逆に言えば、死霊系統は**もともと水増しが無い**。

## 4. 段数を読んでいる場所（3か所）

再定義の影響は倍率だけではない。現行コードで段数を読むのは次の3か所である。

| # | 場所 | 読む値 | 変わること |
|---|---|---|---|
| 1 | `battle.js` `applyDamage()` | イベントの `chainDepth` | 味方のダメージ倍率（3段=×1.25、4段=×1.75、以後+0.25、上限×2.50） |
| 2 | `battle_happenings.js` | `unit.chainDepth >= 3` | 連鎖中ハプニング2種（強欲・臆病）の発火条件 |
| 3 | `run.js` | ランの `maxChain` | 教訓「未完の記憶」(`<=2`)、魔界史のビルド名「N連鎖を通した」(`>=6`) |

**3が最も見落としやすい。** 記録された数字は表示専用ではなく、
`maxChain <= 2` で次ランの応募傾向が変わる（術を扱う者が来やすくなる）。
定義を変えれば、しきい値も一緒に再アンカーしないと**別の教訓が黙って発火する**。

## 5. 影響監査

段数の変更と倍率の変更を混ぜないため、3モードで測る。

- **A 現行**
- **B 段数のみ新定義**（倍率と発火条件は現行の段数で計算する。乱数の呼び出し数が変わらない）
- **C 段数＋倍率**（新定義の段数をそのまま倍率へ渡す）

### 5.1 戦闘そのものは動いていないことの確認（A vs B）

固定編成24戦で、ダメージ列と勝敗の**不一致0件**。
段数の数え方だけでは戦闘計算へ漏れない（＝Bは記録だけが変わる基準として使える）。

### 5.2 段数の変化（味方のダメージ判定 15,841件・150ラン）

| 現行 → 新定義 | 件数 | 倍率 |
|---|---|---|
| 1 → 1 | 14,574 | ×1.00 → ×1.00 |
| 2 → 2 | 1,068 | ×1.00 → ×1.00 |
| 4 → 3 | 182 | ×1.75 → **×1.25** |
| 4 → 2 | 15 | ×1.75 → **×1.00** |
| 3 → 3 | 2 | ×1.25 → ×1.25 |

**倍率が下がる判定は197件＝全体の1.2%**。倍率が上がる判定は0件。

### 5.3 記録された段数（同じseed一覧・200ラン×3seed基）

| 指標 | A 現行 | B 段数のみ | C 段数＋倍率 |
|---|---|---|---|
| 平均 最大CHAIN | 3.77 / 3.80 / 3.81 | 3.10 / 3.11 / 3.08 | 3.03 / 3.02 / 2.99 |
| クリア率 | 47.5 / 45.5 / 42.5% | 47.0 / 44.0 / 40.5% | 48.0 / 39.0 / 41.5% |
| 平均到達ステージ | 7.75 / 7.75 / 7.71 | 7.78 / 7.68 / 7.70 | 7.78 / 7.71 / 7.82 |
| 教訓「未完の記憶」発火 | 0.0 / 0.0 / 1.0% | **21.5 / 22.0 / 28.0%** | 同左 |
| ビルド名「N連鎖を通した」 | 14.0 / 14.0 / 16.0% | **1.5 / 1.5 / 1.5%** | 同左 |

戦略は「最強優先・侵攻のみ」に固定（`tools/sim.js` の基準戦略と同じ手順）。
参考に、本体無改造の `node tools/sim.js 100` は 12〜75%（最強優先49.0%）で、
基準そのものは動いていない。

**読み方**:

1. **勝率への影響は、この試行数では seed差（±5pt）に埋もれる。** 倍率が動くのは1.2%の判定だけで、
   そのうち大半は ×1.75→×1.25。「弱体化する」と断定できる測定にはなっていない。
2. **記録への影響は明確で大きい。** 平均最大CHAINが 3.8 → 3.1 へ確実に下がり、
   ビルド名「N連鎖を通した」は **14% → 1.5%** とほぼ絶滅、
   教訓「未完の記憶」は **0% → 約24%** と、ほぼ出なかったものが4回に1回出るようになる。
   これは倍率とは無関係に、Bモード（段数だけ）で起きる。

## 6. 記録互換

- 保存済みの `st.maxChain` / 魔界史 / KPI `chainMax` は**旧定義の数値**である。
  新旧を同じ列に並べると平均が壊れる。記録側に定義版（例 `chainDefVersion: 2`）を持たせ、
  版が違う記録は同じ集計へ混ぜないこと。旧記録の再計算はできない（タイムラインを保存していない）。
- 第4節の3か所のしきい値（`>=3` の倍率開始点、`>=3` のハプニング、`<=2`/`>=6` の記録）は
  **すべて旧定義の分布に合わせて置かれている**。定義を変えるなら、
  しきい値も新分布へ合わせて置き直すのが1セットの変更である。片方だけ入れない。
- 表示側（`chainSummary.deepest.steps`）は段数をそのまま出すので、
  新定義では「同じ経路なのに段数が減った」ように見える。役（`chainRole`）を併記すれば
  「殴った→伝播した」の2段だと読める。**段数を減らすなら、代わりに役を見せる。**

## 7. 推奨（判断材料）

段数の数え直しと倍率の変更を**同時に入れないこと**を勧める。順序案:

1. **先に役だけ入れる**（`chainRole` を全因果イベントへ付ける。`chainDepth` は現行のまま）。
   表示と戦果が「何が実際に起きたか」を説明できるようになる。倍率も記録も動かないので、
   ここまでは回帰テストだけで安全に入る。
2. **次に、記録のしきい値を新分布へ置き直す**（教訓 `<=2`、ビルド名 `>=6`）。
   置き直してから `chainDepth` を新定義へ替える。逆順にすると、
   教訓が黙って4回に1回発火するようになる。
3. **倍率の段（`>=3` から）は最後**。1.2%の判定しか動かないので、
   まず1と2の見え方を試遊で確かめてから決めてよい。

「深い連鎖ほど強い」という報酬設計自体は変えていない。変えるのは**何を1段と数えるか**だけである。

## 8. 未確認事項

- 勝率への影響は seed差に埋もれており、**「影響が無い」と証明したわけではない**。
  倍率まで入れると決めた時点で、`tools/sim.js` の全15戦略×200で測り直すこと。
- 測定に使った戦略は1つ（最強優先・侵攻のみ）。略奪特化・死霊特化の編成では
  段数の分布が違うはずで、そこでの倍率影響は別に測る必要がある。
- 敵側のCHAINは倍率を受けない（`attacker.side === "player"` 条件）ため、この監査では扱っていない。
- 分類のうち `death` を実効果（+1段）としたのは判断である。
  「撃破は一撃の結果であって別の出来事ではない」と見るなら補足にもできる。
  その場合は上の全経路がさらに1段下がるので、採るなら測り直しが要る。
