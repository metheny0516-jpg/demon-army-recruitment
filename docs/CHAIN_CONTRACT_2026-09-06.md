## 1. いまの定義とその問題

`emitCausal(type, data, parent)` は、親を持つ因果イベントの深さを**種類を問わず**
`parent.chainDepth + 1` にしている。その結果、**同じ一つの効果を言い換えただけのイベントも
1段として数える**。

実測（OVERKILL系統）:

```
生1  attack                        殴った
生2  overkill                      その一撃の余剰を言い換えただけ
生3  trait_trigger(chain_massacre) 「伝播する」という宣言
生4  splash                        実際に伝播したダメージ
```

プレイヤーから見た出来事は「殴った → 余りが次へ流れた」の2つ。記録は4段。
その4が、そのまま**ダメージ倍率 ×1.75** になっている。

## 2. 契約案

### 2.1 数え方の原則

**同じ実効果を一度だけ数える。** 計算がどこで行われているかは分類に使わない。

| 役 | 定義 | 段数 |
|---|---|---|
| **実効果** `effect` | 別の能力・規則が起こす、別個の状態変化 | **+1段** |
| **補足** `restate` | 親と同じ一つの効果の言い換え・内訳・修飾 | 増やさない |
| **宣言** `declaration` | 「これから起こす」。効果を担う子があればその子が1段。**担う子が無ければ宣言自体が唯一の表現なので1段** | 子しだい |

「別個の状態変化か」の判定基準は、**その効果を表す別のイベントが親子関係でつながっているか**。
つながっているなら、状態を実際に動かした側だけを数える。

### 2.2 全因果イベントの分類

| イベント | 条件 | 役 | 理由 |
|---|---|---|---|
| `attack` / `splash` | — | 実効果 | HPが減る |
| `death` | — | **補足** | その一撃そのものの結果。別の能力による別個の状態変化ではない |
| `overkill` | — | 補足 | 同じ一撃の余剰の言い換え |
| `survive` | — | **実効果** | 《執念》等が介入してHPを1に固定し、撃破を打ち消す。別個の状態変化 |
| `revive` / `summon` / `heal` | — | 実効果 | 編成・HPが動く |
| `momentum` | — | 実効果 | 味方全員の与ダメージ倍率が上がる |
| `resource_gain` | gold / soul | 実効果 | 予約金貨・魂が増える |
| `resource_consume` | food | 実効果 | 備蓄が減る |
| `resource_consume` | soul | 補足 | 《魂の徴収》の内訳（同じ効果の後半） |
| `resource_forfeit` | — | 実効果 | 予約金貨が没収される |
| `incident` | — | **宣言** | 同士討ちのダメージ（子）が効果を担う。子を持たない種類では宣言自体が1段 |
| `trait_trigger` | `greedy` / `chain_massacre` / `overload` / `glutton_feast` | **宣言** | 追加行動・伝播ダメージ（子）が効果を担う |
| `trait_trigger` | `demon_cook` | **実効果** | 倍率の計算場所は run.js だが、**効果の表現はこの1件だけ**。計算場所では分類しない |
| `trait_trigger` | `big_eater` / `hunger_demon` / `soul_harvest` | 実効果 | 同上（他に担い手がいない） |
| `synergy_trigger` | `goblin_pair` | 実効果 | 次の味方攻撃+25%。担い手は他に無い |
| `facility_trigger` | `extortion_ledger` | 実効果 | 次の味方攻撃+40% |
| `facility_trigger` | `graveyard` | 宣言 | 実効果は子の `summon` |
| `facility_trigger` | `grand_kitchen` | **補足** | 食事強化の修飾。増やしているのは料理人の効果そのもの |

**未分類のイベントが出たら停止する。** 黙って0段扱いにしない
（`tools/chain-audit.js` の `classify()` が例外を投げる）。

### 2.3 結合の向き（採用済み仕様に合わせる）

**宣言は、前の親へではなく、効果を担う直接の子へ吸収する。**
「強欲」と「それが起こした追加攻撃」で1つの step になり、UIは
**「《強欲》による追加攻撃」**と読める。初版（62adfbf）は宣言を親側へ吸収しており、
採用済み仕様と逆だった。

- 結合の判定に使うのは**親子関係だけ**。タイムライン上で隣り合っているかは見ない。
- 効果を担う直接の子とは、実効果の子、または「実効果の子を持たない宣言」の子。

**分岐して実効果の子が複数ある場合（1つの宣言から2体以上が動く等）:
同じ宣言を各子の step へ複製して所属させる。集合stepにはしない。最初の子だけを選ぶこともしない。**
理由は、段数は「実際に起きた効果の数」であり、宣言が1つでも効果が2つなら出来事は2つだから。
UIも「《能力》による○○」を効果の数だけ出せる。複製された側の step には
`sharedDeclaration: true` が立ち、宣言イベント側は `stepIds` に所属先を全部持つ
（`stepId` はそのうち先頭）。

### 2.3.1 行為者（actor）の規則

初版の「行為者は宣言があればその人物」という説明は誤りだったので、次に置き換える。

**`actorId` / `actorName` は「実効果を起こした人物」だけを指す。人物が起こしていない
効果では `null` にする。宣言者は `declaredBy.actorId` / `declaredBy.actorName` に入れる。**

- **分岐では宣言者と実行者が別人になる。** 宣言者を優先すると分岐の全stepが宣言者の
  名前になるので、必ず実効果側を優先する（9件目のテストで検出した欠陥）。
- 効果イベントが行為者を持たない種類（仲間割れの `splash` など）に限り、宣言者で補う。
- **施設が起こす効果には人物の行為者が居ない。** `actor` は `null` のままにし、
  施設は `abilityId` / `abilityName`（`facilityId` 由来）で表す。
- **`summon.sourceUnitId` は行為者ではない。** これは遺骸を提供した**戦没者**であり、
  召喚したのは施設《墓地》である。行為者へ帰属させると「戦没者が自分を召喚した」ことになる。
  戦没者と召喚された個体は**別の役**として `effect.fallenId` / `effect.summonedId` に
  分けて保持し、`targetId` は召喚された個体を指す。
  墓地経路のassertで「戦没者が召喚者にならない」ことを固定してある（3節）。

経路の終端が「効果を担う子がある宣言」だった場合は step を作らない
（その step は経路上に無い子の側にある）。どこへ所属したかは
最後の step の `pendingDeclarations` に残す。

起点が「数えない」種類（子が効果を担う宣言）のときは、段は子から始まる（起点は0段）。

### 2.4 単一API（設計案）

生の因果グラフ（`parentEventId`）はそのまま保持し、読み方だけを与える1つの関数にまとめる。
現行の `Battle.summarizeChains()` と `Battle.deepestChainPath()` はこれ1本に置き換わる。

```js
Chain.summarize(timeline) → {
  defVersion,        // 定義版（2）。記録へそのまま持たせる
  maxDepth,          // 正規化後の最大段数
  rawMaxDepth,       // 生の親子段数の最大（旧定義と同じ値）
  eventCount,
  events: [{         // 各イベントの正規化段数。生グラフは捨てない
    eventId, parentEventId, chainId, type,
    role,            // effect | restate | declaration
    effectKind,      // 同じ実効果を指すイベントは同じ識別子
    rawDepth, depth, counted,
    stepId, stepIds  // 所属する結合単位（宣言が分岐したときは複数）
  }],
  chains: [{ chainId, maxDepth, rawMaxDepth, eventCount }],
  deepest: { chainId, depth, rawDepth, steps: [...] },
  pathTo(predicate) // 任意のイベントで終わる経路を同じ結合規則で取り出す
}
```

`steps[]` は**UIが「《能力名》による行動」と書けるだけの情報**を持つ。
イベントの `text` を解析させない。行為者名は `battle_start` のスナップショットと
`summon` から引く。

```js
steps[] = {
  stepId, depth, rawDepth, effectKind, role,
  actorId, actorName,          // 実効果を起こした人物。人物が起こしていなければ null
  abilityId, abilityName,      // 能力名（《強欲》《墓地》《暴食の宴》…）
  declaredBy: {                // 宣言イベント。無ければ null
    eventId, type, abilityId, abilityName, actorId, actorName
  },
  effect: {                    // 効果そのもののイベント。数値はここから読む
    eventId, type, dmg, amount, resource, label, targetId, targetName,
    // summon のときだけ付く2役。どちらも行為者ではない
    fallenId, fallenName,      // 戦没者（遺骸を提供して倒れた側）
    summonedId, summonedName   // 召喚された個体（targetId はこちらを指す）
  },
  sharedDeclaration,           // 分岐して複数stepへ複製された宣言か
  pendingDeclarations,         // 経路上で効果の子が別枝にあった宣言（任意）
  eventIds, types              // この step を構成した生イベント
}
```

表示例（実測の値をそのまま並べたもの）:

```
step1: attack             / 行為者 盗む役 → 傭兵ガレス
step2: 《追い剥ぎ》 resource_gain / 行為者 盗む役
step3: 《強欲》による attack     / 行為者 反応役 → 傭兵ボルド

step2: 《墓地》による summon → 前衛の骸骨従者 / 戦没者 前衛（召喚者ではない）
```

## 3. 期待経路（assert済み）

`node tools/chain-audit.js --paths` が経路をassertし、一致しなければ監査を中止する。
**段数だけでなく、各 step の構成（実効果の種類と、その行動を起こした能力名）まで**照合する。

| 系統 | 結合後の step 構成（効果の種類／能力名） | 生 → 正 |
|---|---|---|
| 略奪 | `攻撃` → `追い剥ぎ:+1G` → `強欲による追加攻撃` | 4 → 3 |
| 食料 | `糧食消費`（巨大厨房は同じ効果の修飾なので数えない） | 2 → 1 |
| 暴食 | `糧食消費` → `暴食の宴による追加行動` | 3 → 2 |
| 死霊 | `攻撃` → `蘇生` → `魂の徴収` | 4 → 3 |
| 墓地 | `攻撃` → `墓地による召喚`（人物actorなし・戦没者と召喚個体を別役で保持） | 4 → 2 |
| OVERKILL | `攻撃` → `魔王軍完成による伝播ダメージ` | 4 → 2 |
| 仲間割れ（子あり） | `今ここで下剋上による同士討ち` | 2 → 1 |
| ストライキ（子なし） | `戦場ストライキ`（宣言自体を1段） | 1 → 1 |

墓地経路には行為者の帰属についての追加assertが6件ある。
`actorId === null`（人物は召喚していない）／施設は `abilityId === 'graveyard'` で表す／
宣言側にも人物actorを立てない／戦没者が行為者にも召喚個体にもならない／
戦没者と召喚個体を別の役で保持／`targetId` は召喚個体を指す。

最後の2件が、宣言の扱いの両側を固定している。効果を担う子があるときは
**子と1つの step になり**、子が無いときは**宣言そのものが1段**になる。

### 3.1 9件目: 分岐（1つの宣言 → 実効果の子が2件）

**この形は現行の戦闘エンジンでは発生しない。** 理由はコード上の構造で2つある。

- 《強欲》は反応者ごとに**別々の** `trait_trigger` を出し、その1件が1回の追加行動を起こす
  （`battle.js` の `for (const reactor of allies)` → `emitCausal` → `act`）。
  つまり「強欲持ちを複数出撃」させても宣言も子も人数分に増えるだけで、
  1つの宣言に子が2件ぶら下がる形にはならない。
- 《連鎖虐殺》《魔王軍完成》の伝播は次の対象を**1体だけ**選ぶ（`opponents.find`）。

実測でも「強欲×3／連鎖虐殺×2／過負荷×2／暴食の宴×2／混合」の**2000戦で分岐は0件**だった。

それでも正規化APIは分岐を扱う契約になっているので、
**最小の合成タイムラインを直接 `summarize()` へ渡して**契約を固定する
（`sharedDeclarationTimeline()` / `runSharedDeclaration()`）。
合成タイムラインは、本命の枝（`A1 攻撃` → `A2 強欲宣言` → 実効果の子 `A3`・`A4`）、
同じ親を持つ別枝 `A5`、別チェーン `B1→B2→B3` の3系統を含む。assert は20件:

| 観点 | assert |
|---|---|
| 宣言の所属 | `A2.stepIds` が2件で、中身は `['A3','A4']` |
| 最初の子だけを選ばない | `A2.counted === false` かつ `stepIds.length === 2` |
| 別々の段 | `A3`・`A4` がそれぞれ独立した `stepId`、ともに 正2段（生3段） |
| 同じ宣言を指す | 両経路の終端 step の `declaredBy.eventId === 'A2'` |
| 複製の印 | 両 step の `sharedDeclaration === true` |
| 取り違えない | 各 step の `effect.eventId` が自分自身、行為者は実行者（強欲A / 強欲B）、`declaredBy.actorName` は宣言者（強欲A） |
| 別枝を誤結合しない | 同じ親の `A5` は `declaredBy === null`、`A2.stepIds` に `A5` は入らない |
| 別チェーンを誤結合しない | `B2.stepIds === ['B3']`、`B3` は `sharedDeclaration === false`、チェーンは2本 |

本体実装へ移す際は、この20件がそのまま移植対象の契約テストになる。
**実戦で発生しない契約なので、本体側で分岐を新設する変更（1つの宣言から複数体を動かす能力）を
入れた時に、初めてこのテストが実データで意味を持つ。**

## 4. 段数を読んでいる場所（3か所）

| # | 場所 | 読む値 | 変わること |
|---|---|---|---|
| ① | `battle.js` `applyDamage()` | イベントの `chainDepth` | 味方のダメージ倍率（3段=×1.25、4段=×1.75、以後+0.25、上限×2.50） |
| ② | `battle_happenings.js` | `unit.chainDepth >= 3` | 連鎖中ハプニング2種の発火条件 |
| ③ | `run.js` | ランの `maxChain` | 教訓「未完の記憶」(`<=2`)、ビルド名「N連鎖を通した」(`>=6`) |

## 5. 影響監査

### 5.1 測定条件（固定）

- 乱数はすべて vm コンテキストへ渡した seed 付き `Math.random` に通す。
  **事件の選択もコンテキスト側の乱数を使う**（ホストの `Math.random` は使わない）。
- **1ランごとに `localStorage` を空にする。** 魔界史・教訓の持ち越しは無し。
- 戦略は「最強優先・侵攻のみ」1本（`tools/sim.js` の基準戦略と同じ手順）。
- モード: A 現行 ／ B 記録のみ新定義 ／ C 倍率だけ ／ D ハプニング条件だけ ／ E 両方。

### 5.2 戦闘内の同一性（A vs B）

固定編成24戦で、ダメージ列と勝敗の**不一致0件**。
記録の数え直しは戦闘計算へ漏れない。

### 5.3 通常ラン 200件 × seed基3種

| モード | クリア率 | 平均到達ステージ | 平均 最大CHAIN |
|---|---|---|---|
| A 現行 | 42.0 / 47.5 / 46.5% | 7.76 / 7.75 / 7.79 | 3.62 / 3.75 / 3.75 |
| B 記録のみ | 42.0 / 47.5 / 46.5% | 7.76 / 7.75 / 7.79 | 2.52 / 2.64 / 2.56 |
| C 倍率だけ | 46.0 / 47.5 / 45.0% | 7.77 / 7.73 / 7.78 | 2.48 / 2.64 / 2.50 |
| D 条件だけ | 42.0 / 47.5 / 46.5% | 7.76 / 7.75 / 7.79 | 2.52 / 2.64 / 2.56 |
| E 両方 | 46.0 / 47.5 / 45.0% | 7.77 / 7.73 / 7.78 | 2.48 / 2.64 / 2.50 |

- **A と B は3seed基すべてで全件一致**（クリア可否・到達ステージ）。
- **D は3seed基すべてで A と完全に同じ。** ハプニング発火条件の変更は、単独では
  ラン結果を動かさない（発火判定の真偽が変わるのは追加行動の 3.1〜4.0%）。
- **C と E は同じ値。** 動因は倍率だけで、条件変更は倍率変更に何も足していない。
- クリア率の差は +4.0 / ±0 / −1.5pt と向きが揃わず、**seed差に埋もれている**。

### 5.4 消費者①ダメージ倍率

味方のダメージ判定 約21,700件（200ラン）のうち、**倍率が下がる判定は 1.12 / 1.11 / 1.59%**。
上がる判定は0件。内訳の大半は `4→3`（×1.75 → ×1.25）。

### 5.5 消費者②ハプニング発火条件

追加行動 230 / 229 / 328 件のうち、`>=3` の真偽が変わるのは **9 / 7 / 13件（3.1〜4.0%）**。
5.3 のとおり、これ単独ではラン結果に出ない。

### 5.6 消費者③記録（条件一致と、実際の提示・命名を分ける）

| 指標 | A 現行 | B 新定義 |
|---|---|---|
| 教訓「未完の記憶」の**条件一致** (`maxChain<=2`) | 0.0 / 0.0 / 0.5% | **67.0 / 60.0 / 64.0%** |
| 　└ 実際に3択へ**提示された** | 0.0 / 0.0 / 0.5% | **67.0 / 60.0 / 63.0%** |
| ビルド名「N連鎖を通した」の**条件一致** (`>=6`) | 11.5 / 15.5 / 13.5% | 0.5 / 0.0 / 1.0% |
| 　└ 実際に**その名前になった**（先頭一致） | 11.0 / 14.5 / 12.5% | 0.5 / 0.0 / 1.0% |

読み方:

- 教訓は `lessonOffers()` が**当てはまったものを先に、足りなければ残りで埋めて必ず3つ**返す。
  当てはまり率が0%→約64%になると、提示もほぼ同率で起きる（一致64.0%に対し提示63.0%＝
  他の当てはまりに押し出されて漏れる回がわずかにある）。
  **選択率は人の判断なのでここでは測れない。** 提示までが測定範囲。
- ビルド名は `BUILD_TRAITS` の**先頭一致**で決まる。条件一致(11.5%)と実際の命名(11.0%)は
  ほぼ同じで、`chain` より上位の「施設を三度回した」「過剰殺戮の」に負ける回が少しある。
  新定義では**ほぼ絶滅**する。

## 6. 記録互換

- 保存済みの `st.maxChain` / 魔界史 / KPI `chainMax` は**旧定義の数値**。
  新旧を同じ列に並べると平均が壊れる。`Chain.summarize()` が返す `defVersion` を記録へ持たせ、
  版が違う記録は同じ集計へ混ぜない。旧記録の再計算はできない（タイムラインを保存していない）。
- 3か所のしきい値（①`>=3`、②`>=3`、③`<=2` / `>=6`）は**すべて旧分布に合わせて置かれている**。
  定義を変えるならしきい値の置き直しまでが1セット。片方だけ入れない。
  実測の分布は 平均 3.7 → 2.5 なので、③の目安は `<=2`→`<=1`、`>=6`→`>=4` あたりから試す。
- 表示側は段数が減って見えるので、代わりに `steps[].effectKind` を見せる。
  「殴った → 余りが流れた」の2段だと読めるようにする。**段数を減らすなら、役を見せる。**

## 7. 推奨

1. **`Chain.summarize()` を先に入れる**（生グラフはそのまま。`defVersion`・役・正規化段数を返すだけ）。
   `chainDepth` の値も倍率も記録も動かさない。表示と戦果が「何が実際に起きたか」を
   説明できるようになる。
2. **記録のしきい値を置き直す**（③）。置き直してから記録側を新定義へ替える。
   逆順にすると、教訓「未完の記憶」が**3分の2のランで提示される**ようになる。
3. **倍率（①）は最後。** 動くのは判定の約1.1〜1.6%で、クリア率の差はseed差に埋もれる。
   ハプニング条件（②）は単独では結果に出ないので、①と同時でよい。

「深い連鎖ほど強い」という報酬設計は変えない。変えるのは**何を1段と数えるか**だけ。
