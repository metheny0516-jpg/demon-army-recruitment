## 1. なぜ測り直したか（母集団の穴）

`07cb1a9` では、最後まで終わらなかったラン（`Game.deploy()` が falsy を返して
`runOnce` が break し、`endRun()` に到達しないもの）を集計から**単純に除外**していた。
全体では5.2%だったが、**戦略ごとに偏っていた**。

```
seed基1000　精鋭3体：200ラン中 147ラン除外（73.5%）
　　　　　　中盤で精鋭に転換：200ラン中 10ラン除外
```

精鋭3体がほぼ母集団から消えており、「全15戦略×200」の比較になっていなかった。
**精鋭3体はCHAINが最も浅い戦略**（V2で平均2.0・中央2）なので、これを落とすと
V2の低CHAIN率が過小評価される。教訓閾値の判断には特に危険だった。

実際、母集団を揃えたら**V1の教訓該当率が 5.1% → 1.5% へ下がった**。
`23059c3` の 5.1% は、除外されなかった側の未完ラン（`maxChain` を 0 として数えていた分）が
そのまま乗っていた数字である。

## 2. 未完ランの原因（`tools/deploy-falsy-probe.js`）

`Game.deploy()` の falsy 経路は `run.js` に2つしかない。

```
1350行  if (this.activeRoster().length === 0) return null;                        → 出撃者0
1361行  if (!openingBattle && !this.preparePayrollForBattle(notes)) return null;  → 給与不能
```

`deploy()` を包んで（**本体もsim戦略も書き換えず**）、falsy のときだけ
呼ぶ**前**に取った読み取り専用スナップショットで分類した。
`preparePayrollForBattle()` は状態を書き換えるので、原因判定のために呼び直していない。

### 結果: 全件が「出撃者0」。本体不具合ではなく sim.js の戦略ロジック不備

```
seed基1000（修正前）　合計 未完 23/450 (5.1%)　理由の内訳: 出撃者0 23件
　　精鋭3体 22/30 (73.3%)　中盤で精鋭に転換 1/30 (3.3%)　他13戦略 0件
```

給与不能・phase不整合・その他は**0件**。最初の6件の詳細はすべて同じ形だった。

```
── 精鋭3体 / seed 9016865 / 理由「出撃者0」
   phase=formation stage=1 turn=1 day=1 開幕プロト=false 作戦=null
   所持金 10G / 食料 3 / 給与総額 0G / 方針 regular
   給与見積: {"policy":{"id":"regular",...},"affordable":true}
   roster 0体 / combat 0体 / activeUids [] → 出撃者 0体
   応募者: なし
```

**ステージ1・1ターン目・1日目に roster が0体。** `newRun()` の初期 roster は `[]` なので、
このランは**一人も採用しないまま最初の出撃へ進んでいた**。
給与は `affordable:true`（払う相手が居ないので0G）。本体は空の軍で出撃させないという
正しい判断をしている。**本体不具合ではない。**

原因は `tools/sim.js` の精鋭戦略にある。

```js
if (strat.kind === 'elite') {
  if (st.roster.length >= 3 || !st.applicants.some(m => m.salary >= 5)) { Game.skipHire(); break; }
}
```

初回の応募に給与5G以上の者が居ないと**一人も採らずに見送る**。
`pivot`（中盤で精鋭に転換）も同型で、ステージ4以降に安い兵を全員解雇したあと
高給の応募者が居ないと同じ状態になる。

### 修正（戦略の意図を保った最小変更）

**「高給3体だけ」という意図は変えず、軍が空のときだけ見送らない**ようにした。

```js
if (st.roster.length > 0
    && (st.roster.length >= 3 || !st.applicants.some(m => m.salary >= 5))) { Game.skipHire(); break; }
```

空のときは下の通常経路へ落ちる。`chooseIndex` は `elite` なら給与5G以上を優先し、
居なければ最も強い者を選ぶので、選び方の意図も保たれる。
`pivot` 側は採用行が高給だけを `reduce` していて空配列で落ちるため、
高給が居ない回だけ `chooseIndex` へ落とし、採用が通らなかったら
`skipHire` して止める（`continue` のままだと無限ループになる）。

**ゲーム本体（`src/`）は1行も変更していない。**

### 修正後（3 seed基 × 3000ラン）

| seed基 | 未完 | 内訳 |
|---|---|---|
| 1000 | **0 / 3000** | — |
| 2000 | 1 / 3000 (0.03%) | 中盤で精鋭に転換 1件 |
| 3000 | 1 / 3000 (0.03%) | 精鋭3体 1件 |

**73.5% → 0.03%。** 残る2件は別の形で、追いきれていない（7節）。

## 3. 母集団の保証

測定器を「未完なら追加採番で補充する」方式へ変えた。
**各戦略とも有効200ランで必ず揃う。** 揃わなければ集計せずに停止する。

- 補充は N の2倍まで。そこまで出るなら原因の切り分けが先
- 有効ラン数が `15 × N` でなければ `process.exit(1)`
- **未完の件数と戦略別の内訳は、補充しても別途出力する**（隠さない）

再起台帳と `測定V1最大 === record.maxChain` のassertは維持している（`0ebeae7`）。

## 6. 消費者ごとの影響と閾値案（採用・切替はしない）

### 6.1 教訓「未完の記憶」（`maxChain <= 2`）

| V2の閾値 | 当たり方（3 seed基） |
|---|---|
| `<=0` | 0.0 / 0.0 / 0.0% |
| `<=1` | 0.8 / 0.7 / 0.5% |
| `<=2`（流用） | **47.6 / 48.2 / 47.8%** |
| `<=3` | 74.9 / 74.5 / 74.7% |

V1 `<=2` は **1.5 / 1.3 / 1.1%**。

**流用は不可（約36倍）。しかも「V1と同じ当たり方」に寄せる案が成立しない。**
V2の分布は `1` が25件・`2` が1402件と、`1` と `2` の間で断崖になっている。
`<=1` は 0.5〜0.8% で V1 の 1.1〜1.5% より低く、`<=2` は 47.8%。
**その間に置ける値が無い。**

そもそもV1の 1.1〜1.5% は「教訓がほぼ発火しない」状態である。
V1には `0` も `1` も無く `2` が44/3000しか無いのだから、
**教訓「未完の記憶」はV1の時点で死んでいる。**
V2で `<=1` を選ぶことは、その死んだ状態を移植することに等しい。

### 6.2 ビルド名「N連鎖を通した」（`maxChain >= 6`）

| V2の閾値 | 条件一致（3 seed基） |
|---|---|
| `>=3` | 52.4 / 51.8 / 52.2% |
| **`>=4`** | **25.1 / 25.5 / 25.3%** |
| `>=5` | 17.3 / 17.5 / 16.8% |
| `>=6`（流用） | 6.8 / 7.4 / 5.9% |

V1 `>=6` は 27.4 / 28.0 / 27.6%（実際の命名は 19.3 / 20.0 / 19.4%）。

**`>=4` が V1 とほぼ同じ当たり方になる。** 3 seed基で 25.1〜25.5% と安定している。
条件一致と実際の命名が離れるのは `BUILD_TRAITS` が**先頭一致**で、
`chain` より上位の「施設を三度回した」「過剰殺戮の」に負ける回があるため。

### 6.3 KPI

`chainAbilityMax` 平均 3.4 → 1.5〜1.6。
V1が「追加攻撃」「死」「OVERKILL」を能力として数えていたのをやめた分が大きい。
ただし**V1とV2で数える単位が違う**（V1は経路上の生イベント、V2は結合済み step）ので、
同じ尺度の増減として読まないこと。

### 6.4 案

**案A（ビルド名だけ揃える）** ビルド名 `>=4`。教訓は据え置かず別途設計し直す。
ビルド名は `>=4` でV1と揃うので機械的に決まる。教訓は6.1のとおり
「V1と同じ当たり方」に寄せる値が存在しないので、閾値だけでは決められない。

**案B（教訓を実際に働かせる）** 教訓 `<=2`（47.8%）＋ 別条件。
V2の最頻値が `2`（1402/3000）である以上、`<=2` は「連鎖が組めなかった」の意味に**なる**。
ただし2回に1回出るので、戦闘数や敗因と組み合わせて絞る方が素直だと思う。

**案C（段階を分ける）** ビルド名 `>=4` に加えて `>=8`（V2で約3%）を別の名前にする。
V2の分布は上に長い尾がある（最高12）。

**どれも採用していない。** 特に教訓は、閾値の問題ではなく
「`maxChain` の少なさで敗因を語る」設計そのものを見直す論点だと考える。
