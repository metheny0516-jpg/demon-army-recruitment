# CHAIN V2切替前の測定（全15戦略 × 200ラン）

2026-09-07・Opus。対象コミット `62b1554`（統合レビュー到達を確認済み）。
**測定だけである。実装切替・バランス変更・閾値の採用は含まない。**
`Chain.RECORDED_VERSION` は `1` のまま。

再現:

```bash
node tools/chain-v2-measure.js 200 --json out.json
CHAIN_SEED_BASE=2000 node tools/chain-v2-measure.js 200
CHAIN_SEED_BASE=3000 node tools/chain-v2-measure.js 200
```

## 1. 測定の作り

**ゲームは1回しか走らせない。1つの戦闘結果から V1 と V2 の両方を算出する。**
V1用とV2用に別々にゲームを回すと、乱数と分岐が食い違い「定義の差」なのか
「別のランを見ているだけ」なのか区別できなくなる。

- **V1** … タイムラインの raw `chainDepth` の最大値（＝ `Battle.summarizeChains().maxChain`）
- **V2** … 同じタイムラインを `Chain.summarize()` で読み直した `maxDepth`

戦闘結果は `KPI.battleFinished(result)` を包んで受け取る。run.js が `maxChain` を
更新した直後に呼ぶ場所なので、記録が見ているのと同じ結果が渡ってくる。

戦略定義とランの回し方は `tools/sim.js` のものを**そのまま**読み込む
（出力部分だけ切り落として評価する）。写しを持つと sim.js とは別のゲームを測ることになる。
sim.js が変わって目印が消えたら例外で止まる。

教訓・ビルド名は、**同じ `record` の `maxChain` だけを差し替えて** `Game.lessonOffers()` と
`Game.BUILD_TRAITS` の先頭一致に通す。条件一致と、実際に提示・命名されたかを別々に数える。

### 停止条件（1件でも崩れたら測定を中止する）

- `Chain.summarize()` がタイムラインを書き換えた
- raw の `parentEventId / chainId / chainDepth` が読み直しの前後で変わった
- V1の再計算値と `chainSummary.maxChain` が一致しない

3 seed基 × 3000ラン（延べ9000ラン・約12万戦闘）で**停止は0件**。
`parentEventId / chainId / chainDepth`・倍率・ハプニング条件・演出閾値・UI・ゲーム本体は未変更。

- **V2の最頻値は `2`（1286件）。** 同じ実効果を一度だけ数えると、普通の一撃は1〜2段に落ちる。

## 4. 消費者ごとの影響

### 4.1 教訓「未完の記憶」（`maxChain <= 2`）

| | V1 | V2（`<=2` を流用） |
|---|---|---|
| 条件一致 | 5.1% | 47.9% |
| 実際に提示 | 5.1% | 47.8% |

**約9.4倍。閾値をそのまま流用することはできない。**
条件一致と提示率がほぼ同じなのは、`lessonOffers()` が当てはまったものを先に返すため。

### 4.2 ビルド名「N連鎖を通した」（`maxChain >= 6`）

| | V1 | V2（`>=6` を流用） |
|---|---|---|
| 条件一致 | 27.2% | 6.9% |
| 実際に命名 | 19.2% | 4.0% |

**約1/4.8。** 条件一致(27.2%)と実際の命名(19.2%)が離れているのは、`BUILD_TRAITS` が
**先頭一致**で決まり、`chain` より上位の「施設を三度回した」「過剰殺戮の」に負ける回が
あるため。V2で `>=6` を流用すると命名は 4.0% まで落ち、**ビルド名としてほぼ機能しなくなる。**

### 4.3 KPI

| | V1 | V2 |
|---|---|---|
| `chainMax` 平均 | 4.7 | 3.0 |
| `chainAbilityMax` 平均 | 3.3 | 1.5 |

`chainSample`（いちばん条件をまたいだ代表CHAIN）:

```
V1（ゴブリン統一+求人 / 深さ16）:
  追い剥ぎ → 強欲 → 追加攻撃 → 死 → 略奪者の連携 → 恐喝帳簿 → OVERKILL → 魔王軍完成 → momentum
V2（ゴブリン統一 / 深さ10）:
  追い剥ぎ → 強欲 → 略奪者の連携 → 恐喝帳簿 → 追い剥ぎコンビ
```

V1の並びには「追加攻撃」「死」「OVERKILL」が能力として入っている。これらは
**能力ではなく、直前の一撃そのものの結果**である。V2はそれを落とし、
「どの能力が繋がったか」だけを残す。`chainAbilityMax` が 3.3 → 1.5 に下がるのは
主にこの分で、**連鎖が痩せたのではなく、能力でないものを能力と数えるのをやめた**結果である。

ただしV1とV2で `chainAbilityMax` の定義が完全に同じではない点は注意が要る。
V1は `KPI.abilityKey()` が経路上の**生イベント**から拾い、V2は**結合済み step** の
能力名から拾う。宣言と効果が1つの step になるぶん、V2の方が構造的に少なくなる。
「同じものを数え直した差」ではなく「数える単位が変わった差」として読むこと。

## 5. 分類が変わった代表例（構造化経路）

`--json` に12件記録している。典型はこれ。

```
最強優先 / seed 317760：V1 6段 → V2 3段（生 6段）
  step1（生1）: attack / 行為者 ゴーン → 精鋭兵フォス
  step2（生4）: 《連鎖虐殺》による splash / 行為者 ゴーン → 王国弓兵レナ
  step3（生6）: momentum
```

生6段の内訳は `attack → death → overkill → trait_trigger(連鎖虐殺) → splash → momentum`。
V1はこれを6段と数える。V2は次のように読む。

- `death` / `overkill` … **補足**。その一撃そのものの結果であって、別個の状態変化ではない
- `trait_trigger(連鎖虐殺)` … **宣言**。効果は子の `splash` が担うので、子と1つの step になる
- 残る実効果は `attack` / `splash` / `momentum` の3つ

**「連鎖虐殺で1体巻き込んで士気が上がった」という出来事は3つ**であり、V2の3段が実態に合う。
V1の6段は、同じ一撃を3回数えたぶん膨らんでいる。

## 6. 閾値案（材料。採用・切替はしない）

V2でどこに置くとV1と同じくらいの当たり方になるか。3 seed基で安定している。

### 教訓 `maxChain <= N`（V1 `<=2` は 5.1 / 5.0 / 5.1%）

| V2の閾値 | 当たり方 |
|---|---|
| `<=0` | 4.9 / 4.8 / 4.7% |
| **`<=1`** | **5.0 / 4.8 / 4.8%** |
| `<=2`（流用） | 47.9 / 48.3 / 48.2% |
| `<=3` | 74.9 / 74.6 / 74.9% |

### ビルド名 `maxChain >= N`（V1 `>=6` は 27.2 / 27.7 / 27.3%）

| V2の閾値 | 条件一致 |
|---|---|
| `>=3` | 52.1 / 51.7 / 51.8% |
| **`>=4`** | **25.1 / 25.4 / 25.1%** |
| `>=5` | 17.4 / 17.5 / 17.0% |
| `>=6`（流用） | 6.9 / 7.4 / 6.0% |

### 案

**案A（V1の当たり方を保つ）** 教訓 `<=1`、ビルド名 `>=4`。
数値としては最も近い。ただし教訓は**V1の時点で実質死んでいる**（5.1%のほとんどが
「戦闘が一度も起きなかったラン」）ので、「V1と同じ当たり方」を保つことは
「死んだままにする」ことでもある。

**案B（教訓を実際に働かせる）** 教訓 `<=2`、ビルド名 `>=4`。
V2の `<=2` は 47.9%。ほぼ2回に1回出るので多すぎるが、
V2の最頻値が `2`（1286/3000）である以上、`<=2` は「連鎖が組めなかった」の意味に**なる**。
数を絞るなら `<=2` かつ別条件（戦闘数が一定以上、など）を足す方が、
閾値だけを動かすより素直だと思う。この判断は測定では決められない。

**案C（段階を分ける）** 教訓 `<=1`、ビルド名 `>=4`（現行の1種類）に加えて
`>=8`（V2で 3.2 / 3.2 / 2.6%）を別のビルド名にする。V2の分布は上に長い尾があり
（`>=8` が約3%、最高12）、1つの閾値で「連鎖ビルド」を表すより刻める。

**どれも採用していない。** 特に教訓は、閾値だけの問題ではなく
「maxChain の少なさで敗因を語る」設計そのものを見直す余地がある。

## 7. 未確認事項

- **勝率への影響は測っていない。** この測定は記録の読み替えだけで、倍率は
  一切動かしていない（V1の倍率のまま3000ラン走らせている）。
  倍率をV2へ切り替える判断には、別途 `tools/sim.js` での測定が要る。
- 教訓の**選択率**は測定範囲外（人の判断）。提示率までである。
- `chainAbilityMax` はV1とV2で数える単位が違う（4.3節）。同じ尺度の増減ではない。
- ハプニング発火条件（`unit.chainDepth >= 3`）と演出閾値は今回の集計に含めていない。
  戦闘中の値であり、ランの `maxChain` とは別の測定が要る。
- `sharedDeclaration`（1宣言→複数の実効果）は実戦で発生しないため、
  9000ランでも1件も出ていない。
